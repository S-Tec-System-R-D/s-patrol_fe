> 작성 2026-10-14 · **전면 재작성 2026-10-15** (P1·P2 전 항목을 **API 1개씩 개별 재측정**.
> 구조를 **증상 중심 → API 중심**으로 바꿨습니다 — 한 API 를 손볼 때 볼 행이 한 블록에 모입니다.)
>
> 기준 서버: 사내 테스트 · 계정 `333333`(현장관리자, 소속 **사업장 6** + 하위 7·8)
> **문제가 있거나 요청이 필요한 것만** 적었습니다. 정상 동작 항목은 뺐습니다.
> 전체 점검 결과(정상 포함)는 [`api-review-course-point.md`](./api-review-course-point.md).

## 이 문서를 읽는 법

- **블록 = API 하나**입니다. `PUT UpdateCourse` 를 수정하실 거면 그 블록만 보시면 됩니다.
- 한 API 에 증상이 여러 개면 **행이 여러 개**이고, **우선순위는 증상마다** 붙습니다
  (같은 API 안에 P1 과 P3 가 함께 있을 수 있습니다).
- 같은 증상이 두 API 에 있으면 **양쪽 블록에 모두** 적고 `※ 같은 원인` 으로 표시했습니다.
- 코드 수정이 아닌 건(이미 저장된 데이터 정정)은 맨 아래 **[데이터 정정 요청](#데이터-정정-요청)** 으로 분리했습니다.

| 우선순위 | 뜻 |
|:-:|---|
| **P1** | 화면이 틀린 값을 보여주거나 기능이 막힘. **프론트가 우회할 수 없음** |
| **P2** | 프론트가 우회 중이나 고쳐야 함(다른 클라이언트는 그대로 밟습니다) |
| **P3** | 개선·문서화 요청 |
| **Q** | 질문 — 답변만 주셔도 됩니다 |

### 측정 방법

`curl`/PowerShell 로 **실제 화면이 보내는 바디 그대로** 호출한 뒤, 같은 값을 다시 조회해
저장 결과를 확인했습니다. 화면으로 도달할 수 없는 경로(손으로 JSON 을 만들어야 하는 경우)는
**P3 로 낮추거나 제외**했습니다 — 지금 피해가 없고 재발 방지용이기 때문입니다.

# 코스 (Course)

## `POST /api/v1/Course/W/sign/AddCourse` — 코스 생성

| # | 대상 | 증상 | 우선 | 영향 | 요청 |
|:-:|---|---|:-:|---|---|
| 1 | `points` | 받아놓고 **편성을 저장하지 않으면서 200 · `data:true`** 를 준다. 그런데 `totalMin` 은 그 지점들의 구간합으로 채운다 | P3 | 편성이 사라진 걸 호출한 쪽이 알 수 없고, **"지점 0개인데 15분"** 인 코스가 남는다 | **요청 DTO 에서 `points` 제거**. (편성 저장 기능은 필요 없습니다 — 저희는 생성 후 `UpdateCourse` 로 편성합니다) |
| 2 | `totalMin` | 구간합과 **다른 값·음수를 검증 없이 저장**한다. `null`·필드 생략이면 **서버가 정확히 계산한다** | P3 | 총 소요시간이 구간합과 어긋난 코스가 생긴다 | **요청 DTO 에서 `totalMin` 제거**(파생값). 못 지우면 **0 이상 + 구간합과 다르면 400** |
| 3 | 응답 | 생성된 **`courseSeq` 를 주지 않는다**(`data: true` 뿐) | P3 | 생성 직후 상세로 이동할 수 없다. 이름으로 찾아가면 **동명 코스에서 엉뚱한 코스로** 간다 | `data` 에 `courseSeq` 반환 |
| 4 | `siteSeq` | 누락·`0`·없는 사업장(`99999`) 모두 **500** | P3 | 입력 오류가 "서버 장애" 로 보인다 | 400 유효성 오류로 ※ [공통 — 오류 응답](#오류-응답-형태가-4종이다) 과 같은 원인 |

**실측** (2026-10-15 · 사업장 7)

| 보낸 것 | 결과 |
|---|---|
| **화면이 보내는 바디 그대로** (`points` 없음, `totalMin: null`) | ✅ 200 · `pointCount:0` · `totalMin:0` — 정상 |
| `points` 2건(구간 10·5) 동봉 | 🔴 200 · **`pointCount:0`** · **`totalMin:15`** (코스 85) |
| `totalMin: 99`, 지점 없음 | 🔴 **99 저장** (코스 81) |
| `totalMin: -5`, 지점 없음 | 🔴 **-5 저장** (코스 82) |
| `totalMin: null` / 필드 생략 | ✅ **0** — 서버가 구간합을 계산 |

**현재 대응** — 프론트는 타입에서 `points` 를 **지워** 실수로도 못 보내게 했고, `totalMin` 은
**항상 `null`** 을 보냅니다. **웹에서는 발생하지 않습니다.** 남은 위험은 swagger 를 보고
`points`·`totalMin` 을 실어 보내는 **다른 클라이언트(앱·수기 호출)** 입니다.

## `PUT /api/v1/Course/W/sign/UpdateCourse` — 코스 수정 · 편성 · 토글

> 이 엔드포인트 하나가 **기본정보 수정 · 활성화 토글 · 교대 허용 토글 · 지점 편성** 네 가지를 모두 처리합니다.

| # | 대상 | 증상 | 우선 | 영향 | 요청 |
|:-:|---|---|:-:|---|---|
| 1 | `points[].memo` | **받고 200 을 주는데** `GetCourseDetail` 의 `points[]` 에는 **그 필드가 없다**. 저장됐는지조차 확인할 수 없다 | **P2** | 구간 메모 UI 를 만들 수 없다. 읽을 수 없어 매 저장마다 `memo: null` 을 보내게 되고, **다른 경로로 들어간 메모가 지워질 수 있다**(읽을 수 없어 확인 불가) | `GetCourseDetail.points[]` 에 **`memo` 추가**, 또는 쓰지 않을 거면 **요청 DTO 에서 제거** |
| 2 | `courseSeq` 누락 | 유효성 오류인데 **401** 이 온다. `courseSeq: 0` 도 401. (없는 번호 `99999` 는 400 으로 정상) | **P2** | 프론트 인터셉터가 **토큰 만료로 오해**해 재발급→실패→**로그아웃**. 저장하려다 로그인 화면으로 튕긴다 | **400 으로** |
| 3 | `totalMin` | `AddCourse` 와 동일 — 보낸 값을 검증 없이 저장(음수 포함). `null`·생략이면 **구간합으로 정확히 재계산**한다 | P3 | 위와 동일 | 요청 DTO 에서 제거 ※ `AddCourse` #2 와 같은 원인 |
| 4 | `points` | **전량 교체**다 — 빠진 행은 삭제된다. 생략·빈 배열도 전량 삭제하고 200 | P3 | 동작 자체는 받아들입니다 | **API 문서에 "전량 교체" 명시.** 아래 실측(식별 규칙)도 함께 적어 주시면 좋겠습니다 |
| 5 | 메서드·필수값 | 코스만 **`PUT`** 이다(지점은 `PATCH`). `UpdateCourseDto` 에 **required 가 하나도 없다** | P3 | 부분 갱신 동작을 호출부마다 확인해야 한다 | `PATCH` 로 통일 + 최소 `courseSeq`·`siteSeq` 를 required |

**실측 — `totalMin` 재계산** (2026-10-15 · 코스 80)

| 보낸 구간(합) | 보낸 `totalMin` | 저장값 | |
|---|:-:|:-:|---|
| 20+30 (50) | `null` | **50** | ✅ 재계산 |
| 20+30 (50) | `99` | **99** | 🔴 검증 없음 |
| **7+8 (15)** | `null` | **15** | ✅ **구간을 줄이면 총합도 따라옵니다** |
| 7+8 (15) | `40` | **40** | 🔴 |
| 3+4 (7) | 필드 생략 | **7** | ✅ `null` 과 동일 |
| 3+4 (7) | `-5` | **-5** | 🔴 음수 통과 |

> ⚠️ **이전 판 정정** — "구간을 줄여도 옛 총합이 남는다 → 재계산을 못 한다" 고 적었는데,
> 그건 `totalMin: 40` 을 **함께 보냈기 때문**이었습니다. `null` 이면 정확히 재계산됩니다.
> **`UpdateCourse` 의 문제는 "보낸 값을 검증 없이 믿는다" 하나뿐입니다.**

**실측 — 편성 행 식별 규칙** (문서화 요청 #4 의 근거)

```
points[].coursePointSeq 를 실어 보내면  → 그 행을 유지한다 (번호 불변: 139·140 → 139·140)
coursePointSeq 를 생략하면              → 삭제 후 재삽입한다 (번호가 새로 발급: 122 → 124 → 126 …)
요청에서 빠진 행                        → 삭제된다
```

**현재 대응** — 바디 생성을 함수 한 곳(`updateCourseBody.ts`)에 모아 `courseSeq`·`points`
전량·`totalMin: null` 을 강제하고 있습니다. 기존 행에는 `coursePointSeq` 를 실어 보냅니다.

# 공통

## 오류 응답 — 형태가 4종이다

**같은 "입력값 오류" 인데 응답이 네 가지**입니다. 클라이언트는 코드별로 다르게 행동하기 때문에
(400 → 메시지 표시 / **401 → 토큰 재발급·로그아웃** / 500 → "잠시 후 다시 시도") 형태가 섞이면
엉뚱한 처리를 합니다.

| 요청 | 응답 | 형태 |
|---|:-:|---|
| `UpdateCourse` · `courseSeq` 누락 또는 `0` | **401** | 래퍼 `{"message":"잘못된 요청입니다.","code":401}` 🔴 |
| `UpdateCourse` · `courseSeq: 99999`(없는 코스) | 400 | 래퍼 |
| `UpdateCourse` · `siteSeq` 누락 | 400 | 래퍼 |
| `UpdatePoint` · `pointSeq` 누락 / 없는 번호 | 400 | 래퍼 |
| `AddCourse` · `courseName` 누락 | 400 | **ProblemDetails** (`errors.courseName`) |
| `DeleteCourse` · `courseId` 누락 | 400 | **ProblemDetails** (`errors.courseId`) |
| **`AddCourse` · `siteSeq` 누락 / `0` / `99999`** | **500** | ProblemDetails 🔴 |
| **`AddPoint` · `authMethod` 누락** | **500** | ProblemDetails 🔴 |
| `AddPoint`·`UpdatePoint` · TAG ID 중복 | **500** | ProblemDetails 🔴 |
| 미사용 지점을 신규 편성으로 추가 | 400 | **빈 body** 🔴 (문서상 빈 body 는 401·403 뿐) |

**요청** (P3, 3건)

1. **입력값 오류는 전부 400 으로.** 특히 `UpdateCourse` 의 `courseSeq` 누락 시 **401** 은
   클라이언트가 토큰 만료로 오해합니다.
2. **숫자 필수값도 문자열처럼 400 유효성 오류로.** 현재 문자열(`courseName`)은 400 +
   `errors` 로 깔끔하게 오는데, 숫자(`siteSeq`·`authMethod`)는 기본값 `0` 으로 통과한 뒤
   DB 단계에서 **500** 으로 터집니다.
3. **메시지에 사유를 담아 주세요.** 변경계 실패가 전부 `"잘못된 요청입니다."` 라서 사유를
   구분·안내할 수 없습니다. `"NFC 값을 입력해주세요."` 처럼 해 주시면 그대로 화면에 띄웁니다.

## `pageSize` 상한 100 — 미문서화 (P3)

상한이 **문서에 없습니다.** 저희가 200 을 보냈다가 **지점 상세의 순찰 기록 조회가 통째로 400**
이었고, 화면에는 "순찰 기록이 없습니다" 가 떴습니다(**장애가 빈 상태로 보였습니다**).
→ 상한 **문서화**. (저희는 100 으로 고쳤습니다.)

## 테스트 환경 CORS (P3)

브라우저에서 직접 호출하면 **전부 차단**됩니다(`Access-Control-Allow-Origin` 없음). 운영은
same-origin 이라 문제없지만, 개발 중에는 **dev 프록시로 우회**하고 있습니다.
→ 테스트 서버에 CORS 설정이 있으면 개발이 수월합니다.
