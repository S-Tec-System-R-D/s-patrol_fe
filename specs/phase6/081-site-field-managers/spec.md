# 081-site-field-managers spec

> 위험도: **B**(본사 사업장 상세에 계정 쓰기 흐름 추가 — 새 API 없음 · 현장 근무자 화면의 `AddUser` · `UpdateUser` · `RemoveUser` 재사용).
> 시안: 없음 — 사업장 상세의 기존 카드(`담당 관리자`) 모양을 따른다.
> 관련: `spec 043`(본사 계정은 현장 사이트 진입 불가) · `041`(근무자 추가 · 수정 · 삭제) · `080`(사업장 상세 좌 400px / 우 배치)

---

## 1. 왜

본사 계정(시스템관리자 · Master · Manager)은 현장 사이트에 들어갈 수 없다(`spec 043`). 현장 사이트의 근무자 추가는 현장관리자가
로그인해야 쓸 수 있고 그 폼은 `현장 근무자`(7)만 만든다. 그래서 **새로 만든 사업장에는 현장 사이트에 로그인할 사람을 만들 길이 없었다.**
→ 사업장의 현장관리자 계정은 **본사 사업장 상세**(`/admin/locations/:id`)에서 만들고 고친다(사용자 2026-11-17).

## 🔴 실측 (WF-1-0 · 2026-11-17 · 테스트 서버 · 시스템관리자 `000000` · 사업장 7)

우리가 만든 계정(사번 `9908101`) 하나만 만들고 지웠고, 끝에 목록이 비어 있음(`[]`)을 확인했다.

| 호출(본사 토큰) | 결과 |
|---|---|
| `UserList?siteId=7&codeSeq=6` | 200 — 현장 관리자만 걸러 준다. 🔴 행에 **연락처가 없다**(이름 · 사번 · 권한 · 등록일뿐) |
| `AddUser` `siteSeq=7` · `codeSeq=6` | 200 / `data: true` — 목록에 `codeName: '현장 관리자'` 로 나온다 |
| 새 계정으로 현장 로그인 | 200 · `code 201` · JWT role `FieldManager` · 자기 사업장 `UserList` 200 |
| `UpdateUser`(이름 · 연락처 · 비밀번호) | 200 — 상세에 반영 · 새 비밀번호로 로그인된다 |
| `RemoveUser` | 200 — 목록에서 빠진다 |

## 범위

| 영역 | 내용 |
|---|---|
| 위치 | 사업장 상세 **왼쪽 열**, `담당 관리자` 카드 아래에 `현장관리자` 카드(사용자 결정) |
| 목록 | `UserList?siteId=&codeSeq=6` — 줄마다 `이름 사번` + `⋯`. 머리에 인원 수 · `+ 추가` |
| 추가 | 창: 이름 · 연락처 · 사번 · 초기 비밀번호 · 비밀번호 확인 · 소속 사업장(고정). 검증은 근무자 추가와 같다(`addWorkerFormSchema`) |
| 정보 수정 | 이름 · 연락처(`EditWorkerForm` 재사용). 연락처는 목록에 없어 **열 때 상세를 받아** 채운다 |
| 비밀번호 변경 | `PasswordForm` 재사용 |
| 삭제 | 확인 창 → `RemoveUser` → 목록 · 사업장 상세(사용자 수) 다시 받기 |
| 빈 상태 | `현장관리자가 없습니다` + 추가해야 현장 사이트에 로그인할 수 있다는 안내 |

### 결정 (사용자 확인 2026-11-17)

- **D1 범위 = 전부**(목록 · 추가 · 정보 수정 · 비밀번호 변경 · 삭제) — 현장관리자가 한 명뿐인 사업장은 잘못 만든 계정 · 잊은 비밀번호를 본사만 고칠 수 있다.
- **D2 위치 = 왼쪽 열 담당 관리자 아래** — 사람 정보가 한 열에 모인다.
- **D3 권한 = 사업장 수정과 같게** — 사업장 수정 · 삭제에 권한 구분이 없으므로(본사 3종 모두) 이 카드도 구분하지 않는다.

### 범위 밖

- 현장 근무자(7) 계정 — 현장 사이트 근무자 화면의 일이다(현장관리자가 만든다).
- 목록의 연락처 표시 — 목록 응답에 없다. 줄마다 상세를 부르지 않는다(필요해지면 백엔드에 요청).
- 사업장 생성 직후 현장관리자 만들기로 이어 가는 안내 — 요청이 없었다.

### 구현 메모

- 추가 폼은 `AddWorkerForm` 을 고쳐 쓰지 않고 `AddFieldManagerForm` 을 따로 둔다 — 그 폼은 **고른 사업장**(`getSiteSeq`)과 `현장 근무자` 를 고정으로 보낸다.
  옵션을 늘려 한 폼으로 묶으면 잘못된 조합(현장에서 관리자 생성)이 타입을 통과한다. 스키마 · API 함수는 공유한다.
- 정보 수정 · 비밀번호 변경은 근무자 폼을 그대로 쓴다 — 성공 문구가 `근무자 정보를 수정했습니다.` 다(현장 근무자 화면에서 현장 관리자를 고칠 때와 같은 문구).
- 캐시 키는 근무자 화면과 같다(`userKeys`) — 본사 · 현장은 같은 브라우저 세션에서 섞이지 않는다.
