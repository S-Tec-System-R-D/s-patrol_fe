## User Stories

- **US1.** 개발자가 `screens.md` 진행도를 **코드 실사로** 맞춘다 — 끝난 것은 ✓, 남은 것은 △/✗ 와 **막힌 사유**(API 없음 · 목업 없음 · 정책 미정).
- **US2.** 각 권한(시스템관리자 · Master · Manager · 현장관리자)이 **들어갈 수 있는 화면만** 들어간다. 🔴 본사 관리자가 현장 URL 로 오면 **본사 홈**으로 간다(지금은 현장 로그인으로 튕긴다).
- **US3.** 스크린리더 · 키보드 사용자가 폼 입력칸을 **라벨로** 찾고, 에러를 그 칸의 에러로 듣는다.
- **US4.** 화면 문구(확인 · 빈 상태 · 에러 · 값 없음)가 `design-system.md` §4 규칙을 따른다.

## 2. I/O

### 2-1. US1 — 진행도 실사

- 대상: `screens.md` §1 · §2 · §3 의 ✗/△ 행(현재 12행).
- 방법: 행마다 **라우트 · 컴포넌트 · API 호출이 실제로 있는지** 코드로 확인 → ✓ / △ / ✗ 재판정 + 한 줄 사유.
- 이미 보이는 어긋남(실사로 확정): "순찰지점 삭제" ✗(022 에서 구현) · "비밀번호 변경 / 초기화" ✗(041 근무자에서 구현).
- 남는 ✗ 는 **막힌 사유를 명시**한다 — 랜딩(미착수) · 순찰이력 Export(API 없음) · 진행 중 순찰(화면 미정) · 키워드(목업 없음) · 비밀번호 찾기(명세 없음) 등. 지금 사유 칸이 비거나 옛 계획인 행을 고친다.
- `roadmap.md` Phase 매트릭스 · §10 도 함께 맞춘다.

### 2-2. US2 — 권한 매트릭스

**매트릭스**(본 spec 이 확정 · 테스트로 고정)

| 영역 | 시스템관리자 · Master · Manager | 현장관리자 | 근무자 |
|---|---|---|---|
| `/admin/*` | ✅ | ❌ `/403` (`RequireRoute`) | ❌ 로그인 단계에서 차단(`202`, 토큰 저장 안 함) |
| `/*` 현장 | 🔴 ❌ **본사 홈 `/admin/locations` 로** | ✅ (사업장 선택 후) | ❌ 위와 같다 |
| 본사 화면 안 액션 | 그룹 편집 · 담당 그룹 할당: Manager 숨김 · 관리자 추가: Manager 숨김 | — | — |

- 🔴 **변경 1건**: 본사 계정(`role` = SYSTEM · MASTER · MANAGER)이 현장 영역에 오면 지금은 `siteSeq` 가 없어(본사는 사업장을 고르지 않는다 — 043 결정) **현장 로그인으로** 튕긴다. → **`/admin/locations` 로 보낸다**(사용자 결정 2026-10-23). 판정은 `siteSeq` 검사보다 **먼저** 한다.
- 현장관리자의 `/admin/*` 는 지금처럼 `/403`(정책 유지 — `flow.md` "정책 미정" 문구를 확정으로 고친다).
- 문서 정정: `CLAUDE.md` B1 "Admin 3종은 양쪽 사이트 모두 진입 가능" → 본사 화면만 · `flow.md` §0 같은 서술.
- 테스트: 라우트 × 권한 표를 `AuthGuard` · `RequireRoute` 테스트로 고정(현장 라우트 대표 1개 · 본사 라우트 3개 × 4권한).

### 2-3. US3 — 접근성

- 🔴 **`AppInput` 라벨 ↔ 입력칸 연결**(OQ-F, 020 등재) — `label` 을 쓰면 `useId` 로 `htmlFor`/`id` 를 잇는다(호출부가 `id` 를 주면 그것). 에러가 있으면 `aria-invalid` + `aria-describedby`(에러 문구). 사용처 25파일 — **호출부는 고치지 않는다**.
- `AppFormField`(사용처 4)도 같은 연결 — 자식 컨트롤에 `id` 를 이어 준다(방법은 plan-first).
- 테스트: 근무자 · 관리자 폼 테스트의 placeholder 우회(045 에서 겪음)를 **라벨 조회로** 바꿔 연결을 증명한다(대표 2개 파일).
- `design-system.md` §3 의 나머지(포커스 링 · 색만으로 상태 금지 · 키보드)는 **점검만** — 어긋난 곳이 나오면 목록화해 사용자 판단.

### 2-4. US4 — 콘텐츠 톤

- 기준: `design-system.md` §4(라벨 명사형 · 확인 문구 · 빈 상태 = 상태 + 다음 행동 · 에러 = 원인 + 해결책 · 숫자 단위 · **값 없음 `-`**).
- 방법: 화면 문구를 grep 으로 모아 **위반 목록**을 만들고 → 사용자 확인 → 고친다. 🔴 문구는 사용자가 결정해 온 것이 많다(044 · 045 결정) — **목록을 먼저 보이고 일괄로 고치지 않는다**.
- 이미 보이는 위반: 값 없음을 em dash(`—`)로 쓰는 곳 — 044 사업장 목록 담당 관리자 열 · 045 관리자 목록 담당 그룹 칸 등(§4-5A 는 `-`).

## 3. 제약

1. **새 기능 없음** — 정정 · 연결 · 문구만. 화면 구조는 바꾸지 않는다(A3).
2. 가드 변경은 **본사 → 현장 한 갈래만**. 현장관리자 · 근무자 동작은 그대로.
3. `AppInput` 은 공용이라 **겉모습이 바뀌면 안 된다** — 속성(`id` · `htmlFor` · `aria-*`)만 더한다.
4. 문구 수정은 **사용자 확인 후** — 결정된 문구를 되돌리지 않는다.
5. 전역 규칙(디자인 토큰 등)은 건드리지 않는다.

## 4. 엣지 케이스 (US2 — A급)

| 경우 | 처리 |
|---|---|
| 본사 계정 + 현장 URL(`/zones`) | `/admin/locations` 로 `replace` — 로그인 화면을 거치지 않는다 |
| 본사 계정 + 현장 URL + 예전에 저장된 `siteSeq` 가 남아 있음 | 그래도 본사 홈 — 🔴 role 판정이 `siteSeq` 검사보다 먼저다 |
| 토큰 없음 + 현장 URL | 지금처럼 현장 로그인(`?redirect=`) |
| 토큰은 있는데 role 매핑 실패(근무자 · 모르는 role) | 지금처럼 로그인으로 |
| 현장관리자 + `/admin/*` | `/403` |
| 본사 계정이 `/login`(현장 로그인)으로 로그인 | 지금처럼 `code 1xx` → 본사 홈(020) — 변화 없음 |
