## User Stories

- **US1.** 현장관리자가 상세 화면 상단에서 **숫자 하나만 보고** 상태를 판단한다 —
  지금은 코스와 지점의 요약 칸이 **서로 다른 모양**이라 같은 화면군인데 다르게 읽힌다.
- **US2.** 다음에 요약 칸을 만드는 사람이 **한 컴포넌트**를 쓴다(지금은 공용 하나 +
  지점 상세 전용 하나가 따로 있다).

## 1. 목적

요약 칸(KPI)을 **한 벌로 통일**하고, 목업(`공통상세-kpi.png`) 수준으로 다듬는다.

지금은 **두 벌**이다:

| | 코스 상세 | 지점 상세 |
|---|---|---|
| 컴포넌트 | `AppKpiCard`(공용, 배치관리와 공유) | `PointStats` 안의 로컬 `Stat` |
| 모양 | 카드 4장, **좌측 원형 컬러 아이콘** | 카드 **1장을 세로선으로 3분할** |
| 보조 문구 | 없음 | **있음**(`최근 14일 기준` 등) |

같은 제품의 같은 자리인데 모양이 다르다. 그리고 사용자 평가는 **"유치하지 않았으면
좋겠다"** 였는데, 그 인상의 주범은 **원형 컬러 아이콘 뱃지 + 채도 높은 tone** 이다.

## 2. I/O

### Input
- 기존 그대로. **새 조회가 없다** — 세 화면이 이미 계산해 둔 값을 받는다.

### Output
- 세 화면의 요약 칸이 **같은 컴포넌트**로 그려진다.
- `PointStats` 는 **사라진다**(공용으로 흡수).

## 3. 제약

### 🔴 목업의 4요소 중 **데이터가 있는 것만** 쓴다

목업 카드는 ① 라벨+아이콘 ② 큰 숫자 ③ **가로 바** ④ **기준값 한 줄** ⑤ **증감 뱃지**
로 되어 있다. 칸별로 **채울 수 있는지** 따져 보면:

| 화면 | 칸 | 바 | 기준값 줄 | 증감 뱃지 |
|---|---|:-:|:-:|:-:|
| 코스 | 30일 순찰 수행 | ✗ 기준 없음 | ✗ | ✗ 이전 30일 집계 필요 |
| 코스 | 평균 소요시간 | ✗ | 🔴 **불가** — 기준이 `totalMin` 인데 **구간시간 합과 어긋나 있다**(`spec 033`) | ✗ |
| 코스 | 지점 인증률 | ✅ **비율 그 자체** | ✅ `13 / 21건`(`checkedSum`/`pointSum` 이 이미 있다) | ✗ |
| 코스 | 미인증 지점 | ✗ 분모 없음 | ✗ | ✗ |
| 지점 | 2주 인증 | ✗ | ✅ `최근 14일 기준`(현 문구 흡수) | ✗ |
| 지점 | 최근 순찰 | ✗ **숫자가 아니다** | ✅ `마지막 인증 시각` | ✗ |
| 지점 | 소속 코스 | ✗ | ✅ `이 지점이 포함된 코스` | ✗ |
| 배치 | 나간/온/대기 | ✗ | ✅ 사실 설명 한 줄은 가능 | ✗ |

🔴 **바는 1칸, 증감 뱃지는 0칸이다.** 나머지에 넣으려면 **없는 기준값을 지어내야** 한다 —
"유치해 보인다" 를 고치려다 **틀린 숫자**를 넣는 쪽이 훨씬 나쁘다(A1).

→ **바·증감은 `optional` 로 만들고, 근거 있는 칸에만 준다.** 목업과 다르게 보이는 부분은
**데이터가 없어서**이지 디자인을 덜 따른 것이 아니다.

### 기술 제약

1. **`AppKpiCard` 를 재작성**하고 `PointStats` 를 흡수한다. 🔴 **소비처가 3화면**이라
   배치관리도 함께 바뀐다 — 회귀 확인 대상.
2. **구조**(목업): 라벨 좌상단 / **라운드 사각 아이콘 우상단** / 큰 숫자 + 작은 단위 /
   (선택) 바 / (선택) 보조 한 줄.
3. 🔴 **서버 요청을 늘리지 않는다.** "전월 대비" 를 만들려면 이전 구간을 한 번 더
   조회해야 하는데(코스 상세 진입마다 +1), **그 값을 쓸 화면 결정이 없다** → OQ-031-A.
4. **색 사용을 줄인다.** 아이콘 배경은 **중립**을 기본으로 하고, 색은 **경고(미인증)에만**
   쓴다. 지금 4종 tone 을 칸마다 다르게 주어 **네 칸이 서로 경쟁**한다.

### 비즈니스 규칙

5. 🔴 **인증률에 색을 입히지 않는다**(023 결정 유지). 지점 상태에 **`순찰제외`** 가 있어
   분모를 확신할 수 없고, 영원히 100% 가 안 되는 코스를 빨갛게 칠하면 관리자는 매번
   **없는 문제**를 찾는다. **바는 그리되 색은 중립**이다.
6. **빈 값은 `0` 이 아니라 `—`**(023 결정 유지). 이력이 없는데 `0분`·`0%` 로 적으면
   "순찰했는데 결과가 0" 으로 읽힌다.
7. **보조 한 줄은 "무엇을 센 값인지" 를 적는다** — `최근 14일 기준`, `전체 인증 13 / 21건`.
   🔴 **그럴듯한 해석을 쓰지 않는다**(`양호`·`개선 필요` 같은 평가어 금지).

## 4. 엣지 케이스

> B급 — 공통 규칙을 따르되 이 spec 고유의 것만.

| 상황 | 처리 |
|---|---|

| 좁은 폭 | 4칸 → 2칸 → 1칸. `spec 030` 의 `xl` 기준과 어긋나지 않게 |

## 3-B. 🔴 범위 확장 — "비교 대신 **구성**" (목업 수정안, 사용자 결정 2026-10-14)

착수 시점의 판단은 **"바는 1칸, 증감은 0칸"** 이었다. 목업 수정안 2종
(`코스상세-kpi 수정안.png`·`지점상세-kpi 수정안.png`)이 **그 자리를 다른 방법으로 채운다** —
전월 대비 같은 **외부 비교** 대신, **이미 받아 둔 응답 안의 분포(분모)** 를 보여준다.
그래서 **요청이 늘지 않는다**(§3 규칙 3 유지).

### 칸별 확장 (실측으로 가능 여부 확인, 2026-10-14)

| 화면 | 칸 | 추가 | 근거 | 요청 |
|---|---|---|---|:-:|
| 코스 | 30일 순찰 수행 | **분할 바** + `완료 5 / 진행 1 / 미완료 1` | `CourseHistoryRow.status`(0 진행·1 완료·2 미완료)가 행마다 온다 | 0 |
| 코스 | 평균 소요시간 | **범위 바** + `최단 42분 / 최장 58분` | `actualElapsedTime` min/max — 평균 내려고 이미 파싱 중 | 0 |
| 코스 | 〃 | ~~`설정 +5분`~~ | 🔴 **제외**: 기준이 `totalMin` 인데 **7개 중 4개가 구간시간 합과 어긋남**(B-31) → `spec 033` 뒤 | — |
| 코스 | 지점 인증률 | (이미 구현) | — | 0 |
| 코스 | 미인증 지점 | **분할 바** + 지점별 `엘리베이터홀A 5 / 지하B 3` | 023 C단이 **같은 rows** 로 미인증 목록을 만든다 | 0 |
| 지점 | 2주 인증 | `78%` 뱃지 + 바 + **`인증 7 / 대상 9회`** | 🔴 **결함 수정으로 생긴 `attempted`**(아래) | 0 |
| 지점 | 최근 순찰 | `9시간 전` 뱃지 + **14일 점등 바** | `buckets` 가 이미 있다 | 0 |
| 지점 | 소속 코스 | `A동 순찰코스` **만** | 🔴 **분모(`전체 4개 중`)는 넣지 않는다**(사용자 결정) — 사업장 전체 코스 수는 `GetCourseList` **요청 +1** 이다 | 0 |

### 🔴 확장 전에 결함 2건을 먼저 고쳤다 (실측 2026-10-14, 커밋 `f4cab59`)

분모를 붙이려고 데이터를 들여다보다 **숫자가 틀린 것**을 찾았다. 틀린 값에 근거를 더하면
**더 그럴듯하게 틀린다** — 그래서 확장보다 먼저 고쳤다.

1. **`pageSize` 상한 초과** — 서버 상한은 **100** 인데 `usePointHistory` 가 **200** 을 보내
   지점 상세의 순찰 기록이 **실서버에서 통째로 400** 이었다. 화면에는 "순찰 기록이
   없습니다" 가 떴다(**장애가 빈 상태로 읽혔다**). MSW 가 200 을 받아줘 dev 에서는 멀쩡했다.
2. **미완료를 인증으로 셌다** — `GetPointHistory` 는 미완료(3)와 완료(4)가 **섞여서** 오고
   (실측: 69건 중 미완료 43건) **미완료 행도 `checkDt` 를 갖는다.** `summarizePatrolHistory`
   를 `total`(완료) / `attempted`(전체)로 갈랐다 — 그 `attempted` 가 위 표의 분모다.

### 본문 차트 → **라인**(사용자 결정)

지점 상세 본문의 일별 **막대** 차트를 **라인**으로 바꿔 **추세만** 보여준다. 일별 인증
여부는 KPI 의 **14일 점등 바**가 맡는다 — 같은 데이터를 한 화면에 두 번 그리지 않는다.

### `AppKpiCard` 계약 확장 — **prop 3개만 는다**

바 종류가 넷이 되면서 prop 을 따로 두면 7개가 된다(030 에서 "prop 5개면 뽑지 않는다" 고
한 그 기준에 걸린다). **판별 유니온 하나로 묶는다** — "범위 바인데 분할 조각을 줬다" 같은
조합이 **타입에서 막힌다**:

```ts
bar?:
  | { kind: 'ratio'; value: number }                       // 인증률·2주 인증
  | { kind: 'segments'; parts: { label: string; value: number; tone?: SegmentTone }[] }
  | { kind: 'range'; min: number; max: number; value: number }
  | { kind: 'ticks'; days: boolean[] }                     // 14일 점등
foot?: { left: string; right?: string }                    // 바 양끝 라벨
badge?: string                                             // 값 옆 작은 뱃지(78% · 9시간 전)
```

🔴 **기존 `ratio` prop 은 `bar: { kind: 'ratio' }` 로 흡수한다** — 같은 일을 하는 길을 둘로
두지 않는다.

## 3-C. 🔴 시각 결정 — **색이 아니라 위치로 풀었다** (브라우저 확인 중, 2026-10-14)

재작성 직후 평가는 **"여백이 많고 밋밋하다"**, 이어서 **"칩이 너무 회색이고 라벨이 눈에
안 들어온다"** 였다. 색을 올려 보다가 **되돌렸고**, 최종은 이렇다:

| 요소 | 결정 | 사유 |
|---|---|---|
| **아이콘 칩** | **제목 줄 왼쪽**, 회색 유지 | 🔴 우상단에 떨어져 있으면 제목 줄이 양끝으로 벌어져 **가운데가 빈다** — "여백이 많다" 의 실제 원인이 **색이 아니라 배치**였다. 왼쪽에 붙이면 아이콘+라벨이 한 덩어리로 읽힌다 |
| **라벨** | `font-medium` + 잉크 보강, **색 없음** | 라벨이 색을 가지면 **4칸이 다시 경쟁**한다. "무엇인지" 를 말하는 자리는 굵기·명도로 선다 |
| **뱃지** | 중립 배경 + **진한 잉크** + semibold | 칩이 색을 쓰지 않으므로 뱃지도 과하게 들지 않는다. 🔴 **값에 따라 색을 바꾸지 않는다** — `78%` 가 좋은지 나쁜지를 화면이 판정하게 되는데 **그 기준이 없다**(`순찰제외`, `spec 023`) |
| **색의 자리** | **바가 전담** | 완료(초록)/미완료(빨강) 조각은 **서버가 센 상태값**이라 색의 근거가 있다. 카드가 무채색이 되지도 않는다 |

⚠️ **목업과 의도적으로 다른 점**: 보내 주신 목업 2종은 아이콘이 **우상단**이다. 위 ①의
이유로 **왼쪽**을 택했다(사용자 결정). 나머지(분할 바·범위 바·분모 줄)는 목업을 따른다.

🔴 **"유치해 보인다" 의 주범은 색 자체가 아니라 칸마다 다른 색이 경쟁한 것**이었다 —
그래서 기본 톤은 중립 하나이고, `warning` 은 **근거 있는 칸**(미인증 = 서버가 센 건수)에만 쓴다.
